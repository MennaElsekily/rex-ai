# REX AI – Smart Academy Multi-Agent System

## 1. Project Overview

REX AI is a multi-agent system designed to support educational and training operations. It combines specialized AI agents to help students discover suitable courses, research educational tenders, design curricula, generate educational documents, and create marketing content.

This project is being developed as a graduation project.

## 2. Project Objectives

- Provide personalized course recommendations.
- Research and filter educational tenders and requests for proposals (RFPs) in Egypt and Saudi Arabia.
- Support curriculum development and accreditation alignment.
- Generate professional educational documents in PDF format.
- Assist with educational marketing and campaign content.
- Connect the agents through a shared workflow.

## 3. AI Agents

1. **REX Assistant:** Collects learner requirements and recommends suitable courses.
2. **RFP Research Agent:** Finds, extracts, and filters relevant educational tenders.
3. **Curriculum Agent:** Drafts structured curricula, validates them, repairs what can be repaired safely, revises them as new versions, suggests new courses from the academy catalogue, and compares curricula with approved competency frameworks (evidence-based, never an accreditation claim). Every new curriculum request automatically produces **both an English and an Arabic version** -- the admin never has to ask for a language: the second is a careful translation of the exact same structure (same modules, hours, outcome mappings -- never a second, independently-generated curriculum), saved and linked as a bilingual companion. Each language is validated, edited, approved and downloaded independently; see [Curriculum workflow](#curriculum-workflow-validation-approval-and-pdfs).
4. **Educational Document Generation Agent:** Generates professional educational documents, in English or Arabic, from an *approved* curriculum. Ten document types are supported: course description, course proposal, curriculum PDF, participant guide, instructor guide, presentation outline (a PDF outline), question bank, assessment rubrics, capstone project brief, and learning outcomes and assessment plan. Nine are generated by the model from the curriculum (facts are copied from the curriculum and locked; the model only writes the narrative) and checked before anything is saved; the curriculum PDF is the Curriculum Agent's own PDF of the approved version, offered as a read-only download. An administrator reviews, edits and approves each document and downloads its PDF. Known limitation: with the default small local model (`qwen2.5:3b`), Arabic question banks are not reliably generated; validation stays strict, so a bank that fails the checks is reported and not saved. Sending documents by email is not implemented.
5. **Marketing Agent:** Writes marketing campaigns for an *approved* course, in the course's language: a simple strategy and 1 to 3 variations (2 by default) of social media captions, Facebook/Instagram ad copy, LinkedIn posts, e-mail, WhatsApp messages, headlines and calls to action. The administrator confirms or changes the target audience first, chooses which content to generate, then reviews and edits each variation; every campaign waits for explicit approval and only approved content can be downloaded (Markdown or JSON). Nothing is published, e-mailed or sent. Content that mentions prices, discounts, dates, guarantees, certificates or other facts the course does not state fails validation and is not saved. A field that is only too long or too short (e.g. an ad's primary text over 300 characters, an email subject over 70) is mechanically repaired -- trimmed at a sentence/word boundary, or extended with an already-verified course fact -- before the campaign is ever refused; trimming never hides an unsupported claim. A sentence the checks flag (an unsupported claim such as "no prerequisites" for a course that lists them, characters of another writing system, English glued to Arabic) is removed when the model's own repair left it in -- removed, never reworded -- and a one-letter Arabic prefix glued to an English term only gets its missing space ("و Node.js"). If only some variations still fail, just those are written once more, the model shown the good ones. If the model fails on a channel (a real run looped on an Arabic ad until Ollama aborted), the variations are written one at a time. Everything is checked again by the unchanged rules; anything still wrong refuses the campaign and nothing is saved. When the model writes fewer variations than asked (the local model often writes one long e-mail when asked for two), it is asked for the missing ones only, shown the ones already written; the whole set must still pass every check, including "exactly N, never repeating each other". Measured on 2026-11-12 with `qwen2.5:3b` on the six approved courses (form defaults: all 7 channels, 2 variations): 11 of 12 campaigns were saved (2 of 6 before these repairs); the one refusal was a strategy with the wrong number of steps, which cannot be fixed without inventing content. A course whose own text is corrupted (for example an Arabic curriculum with fragments of other scripts) can still make the model fail; the campaign is then refused and nothing is saved.

### Architecture and routing

```text
Agent 1 (learners):   User -> User interface -> REX Assistant -> Knowledge base / RAG -> REX Assistant -> User
Agents 2-5 (admins):  Admin -> Admin interface / Ask agents / floating assistant -> AdminService
                        -> Central Orchestrator -> RFP Research | Curriculum | Documents | Marketing
                        -> Central Orchestrator (combined, synthesized reply) -> Admin
```

- REX Assistant (`agents/user_service.py`) talks to the knowledge base directly and never passes through the admin orchestrator; the admin orchestrator excludes REX (`register_agents.create_admin_orchestrator`). `tests/test_architecture.py` pins both.
- Every admin agent request -- the Ask agents page and the floating assistant alike -- goes through the one `AdminService.ask` call into the Central Orchestrator. The orchestrator plans which agents to run, runs them in order, gives each agent the results of the steps before it, keeps going when one fails, and returns every result plus one synthesized summary of the whole request.

### REX Assistant: document-based RAG over MCP

```text
Ingestion:  academy documents -> text extraction -> chunking -> embeddings -> ChromaDB      (knowledge_base/pipeline.py)
Each turn:  learner -> REX (agents/rex_assistant) -> MCP (stdio) -> RAG server (agents/rag_mcp_server.py)
            -> language detection -> Arabic->English translation when needed -> query embedding
            -> ChromaDB similarity search -> rerank -> evidence -> MCP response -> REX's model -> answer
```

**RAG owns every retrieval step; REX only calls its MCP tools.** REX imports no ChromaDB, embedding, translation or retrieval code and builds no database filter: it passes course IDs, and the RAG service builds the filter. `tests/test_rex_rag_mcp.py` pins this.

- **Ingestion** (`knowledge_base/pipeline.py`): the documents folder (`REX_DOCUMENTS_DIR`, default `knowledge_base/documents/`; PDF, DOCX, PPTX, XLSX, CSV, JSON, HTML, Markdown, TXT). Text is extracted, chunked (up to 1000 characters with 120 overlap, structure-aware) and embedded with `sentence-transformers/all-MiniLM-L6-v2` (384 dimensions, English). Chunks, embeddings and metadata go to the ChromaDB collection `rex_knowledge` in `REX_VECTOR_DB_DIR` (default `knowledge_base/vector_db/`). Metadata holds the file, page, section, chunk ID, the embedding model, and record fields such as `field_course_id`. Nothing missing is filled in.
- **Translation** (inside RAG, `knowledge_base/language.py`): English is embedded as written. Arabic, Egyptian Arabic, Arabizi and mixed text are translated to English (`Helsinki-NLP/opus-mt-ar-en`) **before** the query is embedded. Latin-script course names, IDs and numbers are kept verbatim; documents are never translated. If the translation fails, nothing is retrieved (status `translation_failed`) and REX says so. Measured on the catalogue, raw Arabic embedded directly by this English-only model is much less reliable than the translated query (see [docs/architecture.md](docs/architecture.md#knowledge-base-rag)).
- **MCP tools** (`agents/rag_mcp_server.py`):
  - `search_knowledge_base(question, retrieval_query?, course_ids?, top_k?)`: the similarity search. It returns the original question, the detected language, the translation, the exact embedded text, the embedding model and dimensions, the collection, and each passage with its file, page, chunk ID, course, reranker relevance and vector distance, plus limitations.
  - `get_course_records(query?, level?)`: the **complete** list of verified course records (a course needs both an ID and a name stated in the documents), optionally narrowed by the request's topic or level. It is not a top-k search.
  - `list_courses()`: course IDs and names, used to recognise course names in questions.

**Three learner modes, one conversation:**

1. **A specific course** ("Tell me more about DA-101", "ما هي متطلبات هذه الدورة؟"): REX recognises the course from the catalogue list and searches with the course's name. It then asks RAG for that course's own passages (by course ID) and answers from them with [n] citations. Follow-ups ("its prerequisites", "كم عدد ساعاتها؟", "the first course") stay on the course. Several matching courses: REX asks which one. Unknown: REX says so.
2. **Personalised recommendations:** REX collects the missing profile answers (background, goal, level, delivery preference, budget, time). Any answer can be skipped, and "Online or offline" means no preference. It then searches with the profile (12 passages). Only courses whose passages that search retrieved can be recommended; the model sees those verified records and their passages and picks record IDs (see below).
3. **Catalogue discovery** ("What courses does the academy offer?", "What Data Analytics courses…", "ما هي جميع الدورات…"): REX lists the courses `get_course_records` returns, every course once, numbered and grouped by department, with facts only as the catalogue states them.

**Grounding (recommendations):** every course is written from its verified record: the exact catalogue name and ID, level, duration, delivery, fee, entry requirements, the prerequisite courses the catalogue lists, and the source file. Anything else is "not stated in the catalogue". Budget and delivery are compared only with stated facts. Invented, renamed or combined courses, unknown IDs and repeats are ignored. A sentence in the model's reason that states a fee, delivery, duration, requirement or another course's topic is removed. A beginner gets beginner courses when one fits, and anything above their level is marked with its entry requirements. With nothing that fits, REX says no suitable course was found.

**Traceability:** each answer's Sources section lists the file, page, course, chunk ID, relevance score, distance and the retrieved text.

### Ask Agents: one conversational interface over Agents 2-5

The Admin dashboard's "Ask agents" section is a chat, not a form: the admin types a request in English or Arabic, and the Central Orchestrator decides which specialist agent(s) handle it, including chained, multi-agent requests ("create a data analysis curriculum, then a course proposal document, then a marketing campaign for it"). A multi-agent reply starts with the orchestrator's summary of every step. A chained request that needs a curriculum approved first pauses, and approving the curriculum (in the chat or the Curriculum section) automatically resumes and finishes the rest of the request, with the result appearing in the chat on its own. 

How a request is planned and answered (`agents/orchestrator.py`):

- **Planning:** the orchestrator picks the agents a request asks for, in order. A chained request ("Create a 30-hour Excel for Business Analysis curriculum for beginners, then a course proposal document from it") runs Curriculum, then Documents. A mixed request ("Find training tenders in Egypt and create a curriculum for a data analytics course") runs RFP Research and Curriculum, and each agent receives only its own part of the request ("Find training tenders in Egypt" / "create a curriculum for a data analytics course"). A request that only mentions a curriculum while asking about tenders stays with RFP Research.
- **Execution:** every planned agent really runs; a failure in one step is reported and the other steps still run.
- **Synthesis:** one numbered line per step with that agent's outcome, the ids it produced (curriculum, companion, document, campaign) and their review status, its warnings, then whether the steps depended on each other ("Steps 2, 3 used the curriculum from step 1." or "These steps ran independently.") and a tally ("Done: 1/2 · Waiting: 1 · Failed: 0"). In English or Arabic, as the admin wrote.
- **Waiting:** a step that needs an approved curriculum pauses until the admin approves it (then resumes on its own). If the Curriculum agent asks a question instead (missing hours or level), the later steps are shown as waiting for that answer, not as failed; once the curriculum exists and is approved, ask for those steps again (they are not resumed automatically in that case).

A generated curriculum shows a review card right in the chat: both languages, their status, an Approve button for each pending version, and their PDF downloads once approved. A REX AI launcher (a floating popover, reusing this exact same chat and conversation) is available from every other admin section; opening it or chatting in it never changes the section you are in.

### Curriculum workflow: validation, approval and PDFs

1. **Generate:** an ordinary request ("Create a 40-hour Digital Marketing curriculum for beginners") produces the English curriculum and its Arabic companion, both saved and linked.
2. **Validate (each language on its own):** deterministic rules (`agents/curriculum_research/validation.py`) check every section, hours, measurable outcome verbs, that every learning outcome is developed by a module and assessed, references, accreditation claims, and the language of every field. The rules are never relaxed to make a curriculum pass.
3. **Repair:** one model repair pass, then safe deterministic fixes (`agents/curriculum_research/safe_repair.py`): hours are rescaled to the requested total; a vague verb ("understand", "know") gets the standard measurable verb ("explain", "identify"); an outcome that no module develops ("LO8 is not developed by any module") is linked to the module that shares its topic words. Each fix is listed in the reply, and the curriculum is validated again. Anything without a safe fix stays.
4. **Status:** a version that passes every rule is **Pending review**; one with remaining problems is a **Draft**, which shows its exact validation problems and cannot be approved until the admin edits it into a valid new version.
5. **Approve:** only an administrator approves, one exact version at a time, each language separately (approving English never approves Arabic). Editing an approved curriculum creates a new version that needs its own approval; the earlier approval stays in the history.
6. **PDF:** the final PDF is generated only when a version is approved, saved against that version, and every render gets its own file (earlier PDFs are never overwritten). Each approved language has its own download; a ZIP of both is offered once both languages are approved. No PDF exists for a draft or a version pending review.

## 4. Technology Stack

- **Language:** Python
- **LLM runtime:** Ollama, model `qwen2.5:3b` (set `REX_LLM_MODEL` in `.env` to try another model for REX, `CURRICULUM_LLM_MODEL` for the Curriculum Agent)
- **Agent workflows:** LangGraph (state graphs) and LangChain (chat models, prompts, structured output)
- **Knowledge base (RAG):** ChromaDB, `all-MiniLM-L6-v2` embeddings, cross-encoder reranking, MarianMT Arabic→English query translation
- **Agent tools:** MCP (five servers: knowledge base for REX, tender tools for RFP Research, curriculum tools for the Curriculum Agent, document tools for the Document Generation Agent, marketing tools for the Marketing Agent)
- **PDFs:** ReportLab with `arabic-reshaper` and `python-bidi` for Arabic, and bundled Noto fonts
- **External data:** World Bank Procurement Notices API, Tavily web search
- **User interface:** Streamlit (`rex_ai_app.py`), English and Arabic (RTL)
- **Testing:** pytest, Streamlit `AppTest`

## 6. Setup

You need Python and [Ollama](https://ollama.com) installed. From the project root in PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
pip install -r requirements-dev.txt   # or requirements.txt to run the app without the tests
ollama pull qwen2.5:3b
```

### Configuration (`.env`)

Create a file named `.env` in the project root (it is gitignored, so never commit it):

```text
TAVILY_API_KEY=your-tavily-key
REX_ADMIN_PASSCODE=choose-a-passcode
```

- Without `TAVILY_API_KEY`, RFP web research is skipped and the reply says so. World Bank research (Egypt) still works; Saudi Arabia needs web research.
- Without `REX_ADMIN_PASSCODE`, the Admin interface is disabled. The User interface still works.
- The passcode is shared: there are no individual administrator accounts. An admin session is recorded in the audit trails as `admin-session-<hash>`, which says which session acted, not which person. After 5 wrong passcodes a browser session is locked out for a minute; the lockout is per browser session, so one person's mistakes do not lock the others out (a ceiling over all sessions still slows down guessing through many new sessions).

#### Tender application emails

Approving a tender automatically *prepares* a personalised application email draft for it -- every approved tender, whatever its submission route -- and never sends it (`agents/rfp_research/applications.py` contains no sending code). The draft uses only the saved Application profile (organisation name, overview, services, experience, qualifications, contact details) and the tender's own fields: it quotes the notice's details and puts first the profile's own sentences most relevant to that tender, so two tenders get two different emails. Missing profile details are left out or replaced by a neutral phrase, never invented. The admin reviews and edits it (subject and body) in the Tender dashboard ("Review application email" in Tender review opens it), sees exactly which address it will go to, and only an explicit confirmation sends it, through Resend (`agents/rfp_research/email_sending.py`). Sending needs the admin's authorisation to submit on the academy's behalf and these settings:

```text
RESEND_API_KEY=your-resend-key
REX_EMAIL_MODE=test
REX_EMAIL_TEST_RECIPIENT=you@example.com
RESEND_FROM_EMAIL=verified-sender@your-domain.example
```

- **The recipient is always `REX_EMAIL_TEST_RECIPIENT`, in test and in production mode alike.** The backend (`email_sending.py`) enforces it: the tender's own contact address is never used as a recipient and is never a fallback; it is only recorded in the send history for reference (shown to the admin as "never used"). If `REX_EMAIL_TEST_RECIPIENT` is missing or not a valid address, sending is refused with a clear error. There is no built-in default recipient. The address shown to the admin before confirming is the one the provider is called with and the one recorded in the send history.
- `REX_EMAIL_MODE` defaults to `test` (anything other than exactly `production` is still test mode). Production mode must be switched on explicitly (`REX_EMAIL_MODE=production`); it changes no recipient, and additionally refuses to send a draft written from demonstration profile data (a saved contact email on the reserved `example.com` domain).
- Automated tests never send email: the provider is replaced by a fake in every test.
- `RESEND_FROM_EMAIL` is optional: Resend only sends from a domain verified in that Resend account, which the academy's own contact address usually is not; when set, mail is sent from this address with the academy's own address as Reply-To.
- The admin can review, edit (subject and body) and save a draft any number of times before sending; a draft can no longer be edited once its one real send has gone out.

### Git and runtime files

The databases and indexes the application writes while running are not source code and are ignored by Git (`.gitignore`): the SQLite files of the agents, their `-wal`, `-shm` and `-journal` companions, the generated PDFs, and the **generated knowledge base**: the ChromaDB index `knowledge_base/vector_db/` and the ingestion's `knowledge_base/metadata/chunk_metadata.json` and `ingestion_manifest.json`.

The knowledge base is never committed. Every clone builds its own from the tracked source documents in `knowledge_base/documents/` with `python -m knowledge_base.pipeline` (see [Knowledge base](#knowledge-base)). An index was committed once, and every branch switch to a branch that still tracked it brought back an obsolete catalogue. The files are now removed from Git's tracking (`git rm -r --cached …`, staged in this working copy); branches created before that change still contain the old copy until the change is merged into them. As a safeguard, the RAG server refuses an index that holds documents missing from the documents folder (status `stale_index`, "Rebuild it: python -m knowledge_base.pipeline").

## 7. Running

```powershell
python -m streamlit run rex_ai_app.py
```

Open the local URL Streamlit prints (usually `http://localhost:8501`). The interface is deliberately simple: a white page, one accent colour (`.streamlit/config.toml`), and in the admin dashboard a sidebar with the nine sections -- Tender review, New tender search, Ask agents, Tender dashboard, Curricula, Documents, Marketing, Application profile and Audit trail. The section you are in changes only when you pick another one in the sidebar (or press an explicit "open in ..." button); approving, saving, downloading, switching language or using the floating assistant never moves you. The welcome screen has two choices:

- **I'm a learner:** chat with REX. Ask for a personalized recommendation (REX asks about your background, goal, level, online/offline preference, budget and time; any question can be skipped), or ask directly about a course. Write in English, Arabic or Egyptian Arabic.
- **I'm an admin:** enter the passcode to open the dashboard. From there you can:
  - run a **New tender search** (countries, training categories, priority organisations or sectors, eligibility notes, deadline range), or ask RFP Research or Curriculum Research in chat;
  - review every tender found (approve, reject, or back to pending), with all extracted fields, the source and submission links; Egypt tenders are flagged for immediate review, Saudi tenders are monitored;
  - see in-app alerts for new tenders;
  - browse the **Tender dashboard** of approved tenders, and the **Audit trail**: one chronological table of every decision (tenders, curricula, documents, campaigns), filterable by area;
  - ask the Curriculum Agent in chat (for example "Create an intermediate curriculum about SQL for business analysts, 24 hours", "make it 30 hours", "Suggest new courses for the Data Analytics department"), then review both languages in the chat card or the **Curricula** section: read each version and its validation result, approve it or request changes (the agent can never approve), edit a draft into a valid version, and download the approved PDFs and the bilingual ZIP;
  - open the **Documents** tab, pick an *approved* curriculum and a document type, generate the document (a multi-module document shows its progress and can take several minutes on a small local model), edit the text the AI wrote, approve the final version and download its PDF (text copied from the curriculum is locked; a document has its own review status; a document that does not pass the checks after the repair attempts is not saved). Choosing **Curriculum PDF** downloads the approved curriculum's PDF without generating anything;
  - open the **Marketing** tab, pick an *approved* course, confirm or change its target audience, choose the tone, the content to generate and 1 to 3 variations, then create the campaign (it can take many minutes on a small local model). Compare the variations side by side, edit them, save drafts as new versions, approve explicitly and download the approved campaign as Markdown or JSON. Nothing is published, e-mailed or sent;
  - approving a tender starts its **application workflow**: REX AI shows how to apply (official portal steps) and prepares a personalised application email draft from the **Application profile** (the academy's real details and documents, entered by you), listing anything missing. Nothing is sent unless you review the draft and explicitly confirm sending (see [Tender application emails](#tender-application-emails)); a tender becomes *Applied* only when you record a verified submission.

The course catalogue is **synthetic demonstration data** for Andalusia Academy. Its courses, fees, schedules, instructors and offers are illustrative, not real.

### Knowledge base

```powershell
# 1. (Re)generate the demo catalogue documents from their structured source
python -m knowledge_base.datasets.andalusia_catalogue.build_documents

# 2. Ingest knowledge_base/documents/ into the vector index.
#    Safe to repeat: replaces changed documents, removes deleted ones, no duplicates.
python -m knowledge_base.pipeline

# 3. Check retrieval quality (Recall@5 and MRR on 32 questions)
python -m knowledge_base.evaluation --eval-set knowledge_base/datasets/andalusia_catalogue/eval_set.json
```

Stop the app before step 2, because the running app holds the index open. To use real academy data, put the files in `knowledge_base/documents/` (or set `REX_DOCUMENTS_DIR`) and run step 2. A deployment searches the index in `REX_VECTOR_DB_DIR` (default `knowledge_base/vector_db/`). Keep one authoritative catalogue per index: ingesting a different documents folder into the same index replaces its documents.

The academy catalogue is the Andalusia Academy documents in `knowledge_base/documents/` (10 files: 14 courses, schedules and fees, instructors, FAQs, admission requirements); they are the only source of academy facts. The index is generated, not committed: after cloning, or after the documents change, run step 2. On the current documents the pipeline indexes 98 chunks from the 10 files. Supported formats are PDF, DOCX, PPTX, XLSX, CSV, JSON, HTML, Markdown and TXT. See [docs/architecture.md](docs/architecture.md#knowledge-base-rag).

## 8. Testing

```powershell
pip install -r requirements-dev.txt
python -m pytest -q
```

The test suite uses no network, no Ollama and no real database, and writes only to temporary files (always run it from the project root: `tests/conftest.py` is what redirects every database and PDF folder to a temporary location).
- **Mocked tests:** the chat model, the MCP server, Tavily and the email provider (no test ever sends an email).
- **UI tests:** Streamlit `AppTest` drives the real page: navigation across the nine sections, approvals, downloads, the chat review card, English and Arabic.
- **Real-model tests (opt-in):** `tests/test_curriculum_real_model_e2e.py` runs the real local model (Ollama) through a full bilingual curriculum generation and then the real page and AdminService on what it produced. `tests/test_rex_real_model_grounding.py` runs REX's recommendation for a fixed learner profile, in English and Arabic, with the real model, embeddings and reranker on the catalogue ingested into a temporary store. `tests/test_rex_real_mcp_e2e.py` runs REX end to end through its real MCP client and the real RAG MCP server subprocess (real translation, embeddings, ChromaDB search, reranking and model) on a temporary index, in English and Arabic, for all three modes. All three are skipped by default; run them with `$env:REX_REAL_MODEL_TESTS = "1"; python -m pytest tests/test_curriculum_real_model_e2e.py tests/test_rex_real_model_grounding.py tests/test_rex_real_mcp_e2e.py` (several minutes).
- **REX grounding regression tests:** `tests/test_rex_grounding.py` runs the full REX -> RAG tools -> recommendation flow on the real catalogue (ingested into a temporary store) and on verbatim programme-record chunks, for the learner profile that once produced invented courses.
- **REX <-> RAG over MCP:** `tests/test_rex_rag_mcp.py` checks the order of operations inside RAG (an Arabic query is translated before it is embedded; English is not translated; a failed translation retrieves nothing), the MCP response fields, the real RAG MCP server subprocess on a temporary index, the three learner modes, complete catalogue listing, and that REX contains no retrieval code of its own.
- **Admin agents through the orchestrator:** `tests/test_admin_workflows.py` checks how real request phrasings are planned (single, chained and mixed requests, English and Arabic), that each agent of a mixed request gets its own part, that a failing agent does not stop the others, the synthesis (ids, warnings, waiting steps, both languages), that every admin action enters the orchestrator and that REX is never in it. `tests/test_architecture.py` pins the two paths.
- **Project safeguards:** `tests/test_project_safeguards.py` checks that only the documents in `knowledge_base/documents/` are ingested, that the index can be recreated identically, that the built index (when present) holds only the current documents and no obsolete catalogue ids, that the generated Chroma and metadata files are untracked and ignored by Git, that stores opened without a path in tests are temporary, and that no test can send a real email (`tests/conftest.py` empties `RESEND_API_KEY` and moves every database, index and PDF folder to a temporary location).
- **Real admin workflows (opt-in):** `tests/test_admin_real_workflows_e2e.py` runs AdminService -> Central Orchestrator -> the real agents, their real MCP servers and the real local model on temporary databases and a temporary index: curriculum -> approval -> resumed document; curriculum -> approval -> resumed campaign; tender search (Egypt, real network) -> approval -> draft -> edit -> send to the configured recipient through a recording provider (nothing is sent); one request running two agents. Run with `$env:REX_REAL_MODEL_TESTS = "1"; python -m pytest tests/test_admin_real_workflows_e2e.py -s` (10+ minutes, needs Ollama and network).
- **Browser acceptance:** done by hand or with a browser driver against a running copy of the app; the steps are in [docs/MANUAL_TEST_PLAN.md](docs/MANUAL_TEST_PLAN.md) (section "Browser acceptance"). Run it against a copy with its own data folders, `RESEND_API_KEY` empty and `REX_EMAIL_TEST_RECIPIENT` set to a test address.
- **Local integration tests:** the real parsers, chunker and pipeline with a real Chroma store in a temp folder. Embeddings are faked.
- **Web search** is offline in every test (`tests/conftest.py`).

Retrieval quality is measured separately by the evaluation command above.
